# 코드 이해를 위한 시작 안내

이 문서는 한글 주석을 추가한 버전의 학습 안내입니다. **실행을 시작하는 곳은 서버의 `ServerMain.main()`과 클라이언트의 `ClientMain.main()` 두 곳**입니다. 둘은 서로 다른 프로그램으로 실행되고, TCP 소켓으로 메시지를 주고받습니다.

먼저 이 문서를 읽고 필요한 Java 파일을 열어 보세요. 실행 방법은 기존 [README.md](README.md)에 있습니다.

## 1. 대학 3학년 수준으로 만들 수 있는 코드인가?

제 판단으로는 **3학년이 자료를 참고하며 진행할 수 있는 중상 난도 프로젝트**입니다. 학년만으로 가능 여부가 정해지는 것은 아니고, Java·스레드·자료구조를 얼마나 사용해 봤는지에 따라 차이가 큽니다.

소켓 통신과 Swing 화면은 네트워크프로그래밍 과제의 핵심에 해당합니다. 다만 이 버전에는 단순한 채팅보다 어려운 포커 규칙과 연결 예외 처리가 많이 들어 있습니다. 처음 버전을 만들 때 안정적으로 동작하도록 여러 기능을 넣어 코드가 복잡해졌습니다.

| 부분 | 필요한 지식 | 읽을 때의 우선순위 |
|---|---|---|
| 서버 접속 수락, 문자 송수신 | Socket, ServerSocket, 스트림, 반복문 | 가장 먼저 |
| 버튼 입력과 서버 응답 표시 | Swing, 이벤트 리스너 | 가장 먼저 |
| 접속자와 게임 상태 관리 | 클래스, 배열, List, Map, Set | 핵심 흐름 다음 |
| 차례와 베팅 진행 | 조건문, 상태 전환, 포커 규칙 | 핵심 흐름 다음 |
| 족보 판정 | 빈도 배열, 조합 완전탐색, 비교 | 게임 흐름을 이해한 뒤 |
| 사이드팟 정산 | 정렬, 배열, 금액을 구간으로 나누는 계산 | 심화 |
| 단일 게임 실행기, 송신 큐 | Executor, BlockingQueue, 스레드 간 역할 분리 | 심화지만 구조는 설명할 수 있어야 함 |
| 중복 종료 방지, 연결 수 제한 | AtomicBoolean, Semaphore | 추가로 사용한 도구의 목적 이해 |

중요한 기준은 코드의 길이나 어려운 이름을 외우는 것이 아닙니다. **누가 정보를 갖고 있는지, 요청 하나가 어느 메서드를 거치는지, 왜 스레드를 나눴는지**를 자신의 말로 설명할 수 있어야 합니다.

## 2. 파일을 읽는 순서

처음부터 가장 긴 `GameTable.java`를 한 줄씩 외우려 하면 흐름을 놓치기 쉽습니다. 아래 순서로 한 번 전체 흐름을 잡으세요.

| 순서 | 파일 | 이번에 이해할 내용 |
|---|---|---|
| 1 | [ServerMain.java](PokerServer/src/poker/server/ServerMain.java) | 서버가 어떤 포트에서 접속을 기다리며, 접속하면 무엇을 만드는가 |
| 2 | [ClientSession.java](PokerServer/src/poker/server/ClientSession.java) | 서버 쪽에서 한 명의 메시지를 어떻게 받고 보내는가 |
| 3 | [Wire.java](PokerCommon/src/poker/common/Wire.java) | 양쪽이 주고받는 문장의 형식과 메시지 경계 |
| 4 | [PokerConnection.java](PokerClient/src/poker/client/PokerConnection.java) | 클라이언트 쪽의 연결·송신·수신 구조 |
| 5 | [ClientMain.java](PokerClient/src/poker/client/ClientMain.java) | 버튼을 누르면 어떤 요청을 보내고, 응답을 받으면 무엇을 바꾸는가 |
| 6 | [GameTable.java](PokerServer/src/poker/server/GameTable.java) | 요청 검사 → 베팅 반영 → 다음 차례/단계 결정 |
| 7 | [Cards.java](PokerCommon/src/poker/common/Cards.java), [HandEvaluator.java](PokerServer/src/poker/server/HandEvaluator.java) | 카드 ID와 족보 비교 |
| 8 | [Pots.java](PokerServer/src/poker/server/Pots.java) | 서로 다른 올인 금액을 어떻게 나누는가 |
| 9 | [TablePanel.java](PokerClient/src/poker/client/TablePanel.java) | 전달받은 상태가 카드 그림으로 바뀌는 과정 |

테스트 파일은 구현 흐름을 이해한 다음 읽으면 됩니다. `SmokeTests.java`에는 가짜 참가자를 사용한 검증이, `RenderPreview.java`에는 테이블 배치를 이미지로 그리는 검사가 있습니다. 실제 TCP 검사는 `tests/network_test.py`입니다. Python은 게임 실행에 필요하지 않습니다.

코드 주석의 **[핵심]**은 발표에서 설명할 중요한 연결 지점이고, **[심화]**는 추가 공부가 필요한 부분입니다. 단순 숫자나 색상 설정은 처음 읽을 때 건너뛰어도 됩니다.

## 3. 세 프로젝트의 역할

| 프로젝트 | 갖고 있는 정보와 역할 |
|---|---|
| PokerServer | 모든 개인 카드, 전체 칩, 차례, 실제 게임 규칙과 승패 |
| PokerClient | 서버가 허용해서 보내 준 상태, 화면 부품, 사용자 입력 |
| PokerCommon | 카드 표현과 통신 문법처럼 양쪽이 함께 사용하는 코드 |

공통 프로젝트가 있다고 서버와 클라이언트가 메모리를 공유하는 것은 아닙니다. 각각의 JVM이 공통 클래스를 자기 프로그램 안에 로딩해 사용합니다. 실제 데이터는 소켓을 통해 전달합니다.

클라이언트는 “60까지 레이즈하겠다”는 요청을 보내고, 서버는 현재 차례와 잔액을 확인해 반영합니다. 클라이언트가 자기 칩을 임의로 수정한 결과를 서버가 받아들이는 구조가 아닙니다.

## 4. ‘콜’ 버튼 한 번을 끝까지 따라가기

각 이름을 Eclipse의 검색이나 Ctrl+클릭으로 찾아가며 읽어 보세요.

1. **ClientMain의 버튼 리스너**: `call.addActionListener(...)`에서 `action("CALL", 0)`을 호출합니다. 콜 금액이 0이면 `CHECK`를 선택합니다.
2. **ClientMain.action()**: 현재 `hand`, `turn`과 함께 `ACT` 메시지를 만듭니다. `amount=0`이어도 콜할 수 있는데, 콜 금액은 서버가 계산하기 때문입니다.
3. **PokerConnection.send()**: 문장을 송신 큐에 넣습니다. GUI는 네트워크 전송 완료를 기다리지 않습니다.
4. **PokerConnection.writeLoop()**: 큐에서 문장을 꺼내 `write()`하고, 메시지 끝의 줄바꿈과 `flush()`를 보냅니다.
5. **ClientSession.readLoop()**: 서버에서 한 줄을 받아 `Wire.parse()`로 해석합니다. `loop.execute(...)`로 게임 스레드에 처리를 맡깁니다.
6. **GameTable.handle()**: 연결 객체로 보낸 사람을 찾습니다. `ACT`인지, 현재 차례인지, `hand/turn`이 맞는지 확인합니다.
7. **GameTable.act()**: `currentBet - p.street`로 콜할 금액을 구하고, `pay()`로 잔액과 납부액을 바꿉니다.
8. **GameTable.progress()**: 다음 사람을 정하거나, 모두 행동했으면 다음 공유 카드를 엽니다.
9. **GameTable.broadcast()/snapshot()**: 각 사람에게 보여 줄 상태를 따로 만들어 보냅니다. 다른 사람의 숨겨진 패는 빈 문자열입니다.
10. **클라이언트의 수신과 화면**: `PokerConnection.readLoop()`가 응답을 받고 `ClientMain.message()`에 알립니다. `invokeLater()` 안에서 상태와 버튼을 바꾸고, `TablePanel.setState()`가 다시 그리기를 요청합니다.

`ACT` 예시는 다음과 같습니다. 아래의 `\t`는 설명을 위해 적은 표기이며 실제 데이터에서는 탭 문자입니다. 핸드·차례 번호는 예시이고 실제로는 서버 상태에서 읽습니다.

```text
ACT\thand=1\tturn=7\taction=CALL\tamount=0
```

통신 타입별 필드 전체는 README의 프로토콜 표를 참고하세요.

## 5. 스레드는 왜 여러 개 필요한가?

읽기 작업은 데이터가 도착할 때까지 기다릴 수 있습니다. 화면 스레드가 소켓 읽기를 기다리면 창이 반응하지 않고, 서버의 접속 수락 루프가 한 사람의 요청을 기다리면 다른 접속을 받기 어려워집니다.

| 실행 흐름 | 맡은 일 | 기다려도 되는 것 |
|---|---|---|
| 서버 main | `accept()`로 새로운 접속 수락 | 다음 연결 요청 |
| 서버의 연결별 reader | 한 클라이언트의 요청 수신 | 해당 소켓의 입력 |
| 서버의 연결별 writer | 큐의 메시지를 실제 송신 | 송신할 메시지와 소켓 쓰기 |
| 서버 game-loop 한 개 | 게임 상태 변경, 차례 제한 시간 처리 | 입력/소켓 전송을 직접 기다리지 않음 |
| 클라이언트 EDT | 버튼, 상태 표시, 화면 그리기 | 긴 네트워크 작업을 맡기지 않음 |
| 클라이언트 connect-worker | 서버 연결 시도 | 연결 성공/실패 |
| 클라이언트 reader/writer | 서버와 송수신 | 입력 또는 송신 큐 |
| 클라이언트 heartbeat | 10초 간격으로 PING 요청 등록 | 스케줄러가 주기 관리 |

게임 상태를 바꾸는 사람은 game-loop 한 개입니다. 여러 reader가 동시에 칩을 수정하지 않고 “이 요청을 처리해 줘”라는 작업을 그 실행기의 큐에 넣습니다. 그 결과 각 요청에 대한 상태 변경이 순서대로 일어납니다. 소켓에 쓰는 작업까지 game-loop가 직접 하면 느린 클라이언트 때문에 테이블 전체가 대기할 수 있으므로 writer도 따로 둡니다.

**차례 제한 시간과 통신 읽기 제한 시간은 다른 기능입니다.** 전자는 행동을 하지 않으면 자동 체크/폴드하는 게임 규칙이고, 후자는 소켓 입력이 일정 시간 오지 않았을 때 연결 오류로 처리하는 기능입니다. heartbeat가 오가면 버튼을 누르지 않아도 통신 연결은 유지됩니다.

## 6. 헷갈리는 Java 문법과 도구

### start(), run(), 메서드 참조

실제 코드의 다음 줄은 새 스레드에서 실행할 작업을 지정합니다.

```java
Thread reader = new Thread(this::readLoop, "server-reader");
reader.start();
```

`this::readLoop`는 `() -> this.readLoop()`와 같은 역할의 메서드 참조입니다. 개념적으로는 아래처럼 풀어서 볼 수 있습니다. 설명용 예시이며 소스를 이렇게 바꿔야 한다는 뜻은 아닙니다.

```java
Runnable task = new Runnable() {
    @Override
    public void run() {
        readLoop();
    }
};
Thread reader = new Thread(task, "server-reader");
reader.start();
```

`start()`를 호출해야 새 스레드에서 작업이 시작됩니다. `task.run()`을 직접 호출하면 현재 스레드에서 실행됩니다. `Runnable`은 작업을 담는 약속이고, 그 자체가 스레드는 아닙니다. `ClientMain`의 `sendChat.run()`은 짧은 작업을 현재 화면 스레드에서 실행하는 의도적인 사용입니다.

### invokeLater()와 execute()

| 코드 | 작업을 맡기는 대상 |
|---|---|
| `SwingUtilities.invokeLater(...)` | 화면을 관리하는 EDT |
| `loop.execute(...)` | 이 서버에서 만든 game-loop 실행기 |
| `loop.schedule(..., 초, TimeUnit.SECONDS)` | game-loop에서 지정 시간 후 실행할 작업 |

이름은 다르지만 “지금 이 스레드에서 직접 처리하지 않고 정해진 실행 흐름에 맡긴다”는 점을 먼저 이해하세요. `schedule()`은 `Thread.sleep()`처럼 게임 스레드를 수십 초 멈추지 않습니다.

### 컬렉션과 공통 문법

| 코드/도구 | 이 프로젝트에서 쓰는 이유 |
|---|---|
| `Map<String, String>` | `action`, `chips` 같은 키로 메시지의 값을 찾음 |
| `List<Integer>` | 카드가 들어간 순서가 있는 목록 |
| `Set<Integer>` | 행동 대기 좌석을 중복 없이 보관 |
| `TreeSet<Integer>` | 팟 구간의 높이를 중복 없이 오름차순으로 정렬 |
| `Deque<Integer>` | 카드 더미 앞쪽에서 한 장씩 제거 |
| `BlockingQueue<String>` | 여러 스레드가 안전하게 메시지를 넣고 꺼내는 큐 |
| `offer(...)` | 큐가 가득 차면 기다리지 않고 실패 반환 |
| `poll(1, SECONDS)` | 최대 1초 기다려 꺼내고, 없으면 null |
| `AtomicBoolean.compareAndSet(false, true)` | 동시에 닫으려 해도 종료 본문은 한 번만 실행 |
| `Semaphore(12)` | 아직 입장하지 않은 연결까지 포함해 동시 소켓 수 제한 |
| `final` 필드 | 저장된 참조/값을 다시 대입하지 못하게 함. 참조 대상 내부의 변경까지 막지는 않음 |
| `static` 메서드 | 객체를 만들지 않고 클래스 이름으로 호출하는 기능 |
| `String... pairs` | 여러 String 인자를 배열처럼 받는 가변 인자 |
| `조건 ? 값1 : 값2` | 조건이 참이면 값1, 거짓이면 값2를 선택 |
| `try (자원 = ...)` | 블록 종료 시 close()를 자동 호출하는 try-with-resources |

`ServerMain`의 소켓 연결 제한 12개와 게임 인원 제한 6명은 서로 다른 제한입니다. 실제 좌석 수는 `GameTable.join()`에서 검사합니다.

## 7. 게임 변수는 금액 예시로 이해하기

| 변수 | 뜻 | 프리플롭에서 20을 낸 뒤 플롭에서 40을 낸 예 |
|---|---|---|
| `chips` | 아직 손에 남은 칩 | 초기 1000이면 940 |
| `street` | 현재 단계에 낸 칩 | 플롭의 40 |
| `contributed` | 이번 핸드 전체에 낸 칩 | 20 + 40 = 60 |
| `currentBet` | 테이블에서 현재 맞춰야 할 단계 총액 | 상대가 총 80까지 올렸다면 80 |
| `owed` | 콜에 필요한 추가 금액 | 80 - 40 = 40 |
| `target` | 레이즈하고 싶은 새 단계 총액 | 총 120으로 올리려면 120 |
| `lastFullRaise` | 마지막 정식 증액 폭 | 40에서 80으로 올랐다면 40 |
| `pending` | 지금 다시 행동해야 할 좌석 집합 | 올린 금액에 응답할 사람들 |

잔액이 충분하고 현재 최소 레이즈 폭이 40이라면, `street=40`, `currentBet=80`에서 `target=120` 레이즈를 할 때 실제 납부액은 `120-40=80`입니다. 새로 올린 폭은 `120-80=40`입니다. **실제 납부액과 레이즈 폭은 다른 값**입니다.

`turnToken`은 차례 식별 번호입니다. 예전 차례에서 보낸 요청이 나중에 도착해도 현재 번호와 다르면 거절합니다. `revision`은 전체 상태 갱신 번호로 보냅니다. 이 버전 클라이언트는 revision을 이용한 추가 중복 제거를 구현하지 않았습니다.

## 8. 2명일 때 첫 핸드를 추적하기

첫 참가자가 A(0번), 두 번째가 B(1번)이고 둘 다 1000점이라고 가정합니다. 처음 시작하면 A가 딜러/SB, B가 BB입니다.

| 상황 | A의 chips / street / contributed | B의 chips / street / contributed | 팟 | 다음 행동 |
|---|---|---|---|---|
| 블라인드 납부 | 990 / 10 / 10 | 980 / 20 / 20 | 30 | A |
| A가 10 추가 콜 | 980 / 20 / 20 | 980 / 20 / 20 | 40 | B |
| B가 체크하고 플롭 진입 | 980 / 0 / 20 | 980 / 0 / 20 | 40 | B |
| B가 플롭에서 40 베팅 | 980 / 0 / 20 | 940 / 40 / 60 | 80 | A |
| A가 40 콜하고 턴 진입 | 940 / 0 / 60 | 940 / 0 / 60 | 120 | B |

단계가 바뀌면 `street`만 0이 되고 `contributed`는 남는 점을 확인하세요. 헤즈업은 프리플롭에는 SB가 먼저, 그 이후에는 BB가 먼저 행동합니다.

## 9. 족보와 사이드팟

`HandEvaluator.best()`는 7장 중 5장 조합 21개를 전부 평가합니다. `five()`는 숫자별 개수와 무늬·연속 여부로 족보를 정합니다. `Rank.score`에는 족보 등급과 비교할 숫자를 중요도 순서로 담습니다. 15를 곱하면서 다음 숫자를 더하는 이유는 카드 숫자가 최대 14이기 때문입니다. 모든 결과를 같은 자리 수로 만들면 족보 등급이 먼저 비교되고, 같은 등급에서는 키커가 순서대로 비교됩니다.

사이드팟은 **각 사람의 납부액 높이로 구간을 나누는 계산**입니다. A가 100, B가 200, C가 300을 냈다고 가정하면 다음처럼 처리합니다.

| 순서 | 계산 | 받을 수 있는 사람 |
|---|---|---|
| 미콜 반환 | C가 혼자 더 낸 100을 반환 → 납부액 [100,200,200] | C에게 반환 |
| 메인팟 | 0~100 구간: 100 × 3 = 300 | 폴드하지 않은 A/B/C 중 최고 패 |
| 사이드팟 | 100~200 구간: 100 × 2 = 200 | 폴드하지 않은 B/C 중 최고 패 |

A가 가장 좋은 패여도 받을 수 있는 팟은 300까지입니다. C에게 돌아간 미콜 100은 승리해서 얻은 금액이 아닙니다. 동점이면 해당 팟을 나누며, 1점 단위로 남는 칩은 딜러 다음 순서의 해당 공동 승자부터 줍니다.

짧은 올인의 재레이즈 권한 같은 예외 규칙은 기본 흐름 다음에 읽으세요. `GameTable.mayRaise()` 주석에 100 → 150 → 180 예시가 있습니다. 처음부터 이 예외 하나에 멈추기보다는 정상 콜·정상 레이즈가 어떤 변수를 바꾸는지 먼저 따라가면 됩니다.

## 10. 발표에서 직접 설명할 핵심

아래 문장을 코드 위치와 연결해서 설명할 수 있으면 구조를 이해했는지 점검할 수 있습니다.

- **다중 접속**: ServerMain은 accept를 반복하고, 연결마다 ClientSession의 I/O 스레드를 만든다.
- **메시지 경계**: TCP 스트림에서 줄바꿈을 메시지 끝으로 약속하고 Wire.readLine으로 한 줄을 복원한다.
- **동시성**: 소켓 읽기는 연결별로 하되, 게임 상태 변경은 단일 game-loop로 모아 순서대로 처리한다.
- **화면 반응**: 소켓 대기는 별도 스레드, Swing 변경은 EDT에서 처리한다.
- **검증**: 버튼이 비활성화되어 있어도 서버가 차례·잔액·핸드 번호·차례 토큰을 다시 검사한다.
- **개인 패 보호**: snapshot(viewer)가 상대의 비공개 카드 값을 보내지 않는다. 화면에서만 덮어 그리는 방식이 아니다.
- **게임 규칙**: act가 행동을 반영하고, progress가 다음 사람/단계를 결정하며, finish가 판정과 칩 정산을 한다.
- **역할 분리**: HandEvaluator는 패의 강도, Pots는 금액 분배를 계산한다. UI와 네트워크 코드를 이 계산에 섞지 않았다.

현재 버전은 한 테이블의 기본 게임입니다. 로그인·재접속 복구·DB 전적·여러 방·대회용 데드 버튼 등은 포함하지 않습니다. 실제 코드가 처리하는 범위까지만 설명하면 됩니다.

## 11. 이해를 확인하는 작은 연습

코드를 바로 바꾸기 전에 다음 결과를 먼저 예상해 보세요.

1. ClientSession에서 `table.handle(...)`을 `loop.execute(...)` 없이 직접 부르면 어떤 공유 상태를 동시에 바꿀 수 있을까?
2. `flush()`를 제거하면 어떤 표시 지연이 생길 수 있을까? 메시지 경계를 정하는 것은 무엇일까?
3. `street=20`, `currentBet=60`, `chips=30`인 사람이 CALL하면 잔액·추가 납부액은 얼마가 될까?
4. 한 사람만 폴드하지 않고 남았을 때 공유 카드 5장을 끝까지 뽑을 필요가 있을까?
5. 다른 사람의 패를 클라이언트에 전송한 뒤 화면에서만 가리면 왜 충분하지 않을까?
6. `pending`이 HashSet인데도 차례가 일정하게 유지되는 이유는 무엇일까?

확인할 내용: 1번은 칩·차례·pending·공유 카드 상태의 경쟁 문제, 2번은 출력 버퍼와 줄바꿈의 역할 구분, 3번은 30점 올인 콜 후 잔액 0, 4번은 족보 비교 없이 폴드 승리, 5번은 클라이언트가 이미 비밀 정보를 가진다는 점, 6번은 progress가 집합의 순회 순서 대신 좌석 번호를 직접 돌며 찾는다는 점입니다.

이후 자신의 복사본에서 초기 칩이나 행동 제한 시간을 바꿔 결과를 확인해 보세요. Eclipse 실행은 수정한 소스를 사용하지만, 기존 dist의 JAR은 자동으로 바뀌지 않습니다. JAR로 실행할 때는 먼저 build.bat 또는 build.sh로 다시 빌드해야 합니다.
